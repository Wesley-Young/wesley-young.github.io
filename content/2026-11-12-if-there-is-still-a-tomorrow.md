最近这两天发生的事，想必各位读者多少都有些了解吧——

> 两个基于[腾讯公司](https://zh.wikipedia.org/wiki/%E8%85%BE%E8%AE%AF)[在 1999 年出品的即时聊天软件](https://zh.wikipedia.org/wiki/%E8%85%BE%E8%AE%AFQQ)的[机器人](https://docs.openclaw.ai/zh-CN/channels/qqbot)爱好者社群中[顶梁柱](https://zh.wiktionary.org/wiki/%E9%A1%B6%E6%A2%81%E6%9F%B1)级别的[协议端](https://12.onebot.dev/glossary/#onebot-onebot-implementation)（所谓[一个机器人第十一版协议](https://github.com/botuniverse/onebot-11)的实现）——[雪 · 露玛](https://github.com/SnowLuma/SnowLuma)（仓库已滚木化）和[打盹 · 恶妇](https://github.com/NapNeko/NapCatQQ)，在两三个[地球日](https://zh.wikipedia.org/wiki/%E6%97%A5)内相继宣布[跑路](https://zh.wikipedia.org/wiki/%E8%B7%91%E8%B7%AF)。前者在 9 日晚宣布收到腾讯方[律师函](https://zh.wikipedia.org/wiki/%E5%BE%8B%E5%B8%88%E5%87%BD)，并随即将仓库转为私有；后者则在 10 日在仓库的 [`读我.麻豆`](https://github.com/NapNeko/NapCatQQ/blob/main/README.md) 中添加暂停维护标记，11 日对仓库进行[强制推倒](https://github.com/NapNeko/NapCatQQ/compare/72912f293924f43463b5976b01fc094a8ae11481...363a59563d713064853542053d21c7936a38dadd)，只保留读我文件，解散大部分[群组](https://zh.wikipedia.org/wiki/%E7%BE%A4%E7%BB%84)。

以上内容是对 [cubk 先生](https://cubk.cn/)文风的拙劣模仿。笔者很遗憾在撰写前两篇锐评 QQ Bot 圈新闻的 Blog 时没有来得及拜读这位先生的大作，否则，笔者早就会把所有锐评的文章都按照这一风格撰写了。笔者既身为[协议端的 1.5 线开发者](https://github.com/LagrangeDev/acidify)，又对 NapCat [怀有复杂的感情](./2026-02-21-biography-of-napcat.md)，顿有唇亡齿寒、兔死狐悲之感，今日心血来潮，将这些想法记录下来。

## 养鱼热潮的兴起

自从 LLM 产生以来，将其接入各大传统即时通讯平台一直都是一众开发者的永恒追求。Chatluna、AstrBot 乃至 OpenClaw 都是开发者这方面的尝试，就连笔者也做了一个 [Chatsalt 插件](./2026-08-24-refine-a-role-play-ai-chatbot.md)来实现这一目标。今年 10 月 17 日，DeepSeek 上线了新版本的 Flash 模型，版本号保持为 4.1，但检查点明确为 `1017`。B 站之类的平台一直都会针对 LLM 相关话题上线热搜和推送，颇有一种“大模型厂商放个屁都要让全站用户知道”的味道，因此笔者难以理解的就是为什么只有这次的模型更新掀起了社交媒体上的养鱼热潮。但无论如何，这次 1017 上线之后，「养鱼」这个概念就在整个中文互联网上爆火了。

值得注意的是，作为头部协议端，NapCat 也曾经在其 README 中公开宣传 Mai-Bot、AstrBot 等应用端框架；今年 3 月随着 OpenClaw 的爆火，互联网上也掀起过「养虾」的潮流；但这些宣传都远没有「养鱼」这一概念深入人心。笔者觉得，也许并不需要一个特殊的理由，仅仅是一个试作的项目、一个在 B 站的宣发视频，大概就有引发蝴蝶效应的潜力。[qq-bridge](https://github.com/Derpyu520/qq-bridge) 这个项目就是一个很具有代表性的例子，在其[归档公告 Issue](https://github.com/Derpyu520/qq-bridge/issues/180) 中，开发者就提到这一项目在刚开始宣发时仅有可怜的 3 Star，但截至其停止维护已经拥有了 3k+ 的 Star. qq-bridge 的 README 中明确提及了其对接的协议端是 SnowLuma，因此 SL 当然也在这波养鱼的热潮中吃饱了流量。而至于 NapCat，虽然当时已经成为了开发团队的“弃子”，但至少瘦死的骆驼比马大，也沾到了不少光。

与此同时，养鱼的热潮也给不少人带来了很明显的困扰。至少在笔者的记忆中，笔者所在的多个群聊都遭到了“肥鱼”的围攻，随口说一句话，回应笔者的恐怕就可能是某个群友部署的肥鱼。更要命的恐怕还要数这两个协议端**一脉相承**的默认触发命令了——任取一个群聊发送 `#napcat` 或 `#sl`，几乎都会有部署了 NapCat 或 SnowLuma 的机器人响应。笔者很难猜测 NapCat 当初加入这一主动触发方式的目的是什么，但至少它确实提供了一种很方便的用来抓肥鱼的方法，一些禁止机器人的群聊就用这种几近于“钓鱼执法”的方式识别群聊里部署的机器人并踢出。

## 律师函打击

在养鱼热潮期间，腾讯官方其实早就尝试进行过管控：首先是推出了官方项目 [dsh-qqbot](https://github.com/tencent-connect/dsh-qqbot)，引导用户接入官方 Bot 生态而非第三方协议端；随后又在“QQ 安全中心”公众号发布了[文章](https://mp.weixin.qq.com/s/hNLhLK07BpblMt0C2fkWmQ)以警告使用第三方协议端的用户。奈何第三方协议端社区的舆论风向早已是「协议端影响官方强推自家生态赚钱，因此被打压」，使得上述宣传收效甚微。笔者认为，上述两个管控实则是腾讯的最后通牒。在警告无果之后，腾讯便在 9 号真的动了手，首当其冲的便是 SnowLuma，遭受律师函打击而无奈跑路。受此影响，上面提到的 qq-bridge 也在 11 日宣布进入归档状态。

腾讯的打击发生之后，QQ Bot 圈迎来了一次地震。多个开发者在 B 站发布视频对腾讯的行为进行批评，更有无数用户在腾讯有关养鱼的[视频](https://www.bilibili.com/video/BV17rxT6UEpH)评论区对腾讯发起冲锋。SL 的原仓库不复存在，但 GitHub 上出现了许多自发的 Fork 与备份，并且有不少用户宣称自己将接手对 SnowLuma 的后续维护。已经部署的 NapCat 和 SnowLuma 实例并没有因为这次打击而立刻失效，但随着社群的逐渐解体，不少“难民”也逐渐将目光转向尚且幸存的协议端群聊——虽然这几乎是徒劳的，因为至少在成文的时间，他们是很难取得现有协议端的使用权限的。

## 幸存者

笔者并不清楚自己的项目会不会步 SL 的后尘；但至少截至成文之时，acidify 方面尚未收到腾讯方面发送的任何文件。这大概是因为，早在养鱼热潮兴起之初，包括笔者在内的部分协议端框架维护者就嗅到了可能的危险，及时关闭了新用户注册或加群；而面对这样的威胁，没能及时采取措施的 SnowLuma，便毫不意外地成为了腾讯首先打击的倒霉蛋。笔者并不想对 SL 的项目本身进行过多评价；但回顾 NapCat 和 SnowLuma 一路的发展，笔者不得不感叹一句：**眼看他起高楼，眼看他宴宾客，眼看他楼塌了。**

虽然笔者今年 2 月的[文章](./2026-02-21-biography-of-napcat.md)已经对 NapCat 的发展进行了简要回顾，但也请允许笔者再进行一些补充。2025 年下半年起，NapCat 的社群就逐渐与 Mai-Bot、AstrBot 之类的应用端项目相互绑定，并且 NapCat 的 README 中也明确对这些应用端项目进行了宣传。不少开发者对这样的发展模式表达了担忧，而这次的打击也证明了这些担忧绝非杞人忧天。此外，从 NapCat 到 SnowLuma，各种一键安装包和桌面部署版层出不穷，新用户的使用门槛一路降低，最终导致了在这次的养鱼热潮中，使用者的数量迅速膨胀，这当然也是腾讯采取行动的一个重要原因。面对一个用户众多且鱼龙混杂、具有显著盲目性和冲动性的群体，低调求生、谨慎行事，或许才是最明智的选择。

顶梁柱接连倒下，整个 QQ Bot 圈随之动荡不安。但至少社区的基本盘尚在，笔者会持续维护 acidify，并且在 LLM 编程的加持之下，总会有新的社区项目破土而出（当然不包含 [SnowCatQQ](https://github.com/DandanLLab/SnowCatQQ) 这样的如蛆附骨之跳梁小丑）。历史能够从这次事件中吸取多少教训，我们不得而知。但故事仍然没有结束，至少，如果还有明天，笔者希望 QQ Bot 圈的开发者们能够更加谨慎地行事，避免重蹈覆辙。

最后，还是用《老男孩》的歌词来结束这篇文章吧：

> 如果有明天/祝福你亲爱的
